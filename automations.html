02 What it does

Quiet until it matters.

  1. Weekday digestEach afternoon it lists the incomplete forms, so loose ends get chased the same day.
  2. Weekly site checkEach week it checks site diaries, walks, toolbox talks and observations, and drafts one email per project to forward to the site manager.
  3. Monthly report checkEach month it confirms every active project has filed its safety report for the month just ended, and says which hasn’t.
  4. Fortnightly updateEvery second week it creates a task to present an update, with the details ready.

05 Principles

A job that fails silently is worse than no job at all.

  • Quiet by defaultNothing is sent when there is nothing to say, so the emails get read.
  • Read-only connectionsThe jobs can read other systems and create a task or email, but never delete or overwrite anything.
  • Watch the watchersEvery job is checked for a live schedule, because the worst failure is the one nobody notices.
  • Never twiceEach run is recorded, so a retry can’t send the same report twice.
06 How it’s built

Small services on a timetable, each built to fail loudly.

  • JobsEach automation is its own small Node.js service on Railway’s cron scheduler, with Melbourne-time guards so the same code behaves on holidays and weekends.
  • EmailResults go out through the Microsoft Graph mail API as a named sender, in a branded layout grouped by project.
  • Source dataThe site-management platform is read through its MCP server, limited to a read-only list of tools, with a rotating sign-in token.
  • StateA Postgres record of each run makes jobs idempotent, so a retry can’t send the same report twice.
  • MonitoringA daily check calls the hosting platform’s API to confirm every job still has a schedule, and emails an alert if one doesn’t.
